## 1. 任務定義

兩台**不同型號**的 VTOL 固定翼，在**同一個作業場景**中協同完成一次覆蓋偵查。
不是兩趟獨立任務，是一次任務裡的分工。

超出範圍（本期不做）：三台以上、動態重規劃、空中重新分配、對抗環境。

## 3. 必須先修的阻擋項

這四項在修好之前，**任何分配設計的 A/B 都在量缺陷而不是量設計**。

### B1. Dubins 路徑計算是錯的 —— 最高優先

**[驗證]** 三種**結構獨立**的實作交叉驗證（正規化閉式、切圓幾何、
以及只用前向積分運動學的數值打靶求根），一致到 1e-12；
36,864 組姿態的完整掃掠。

**缺陷分佈（依控制字）**：

| 字 | repo 幾何有效率 | 尖點 |
|---|---|---|
| LSL / RSR / LSR / RSL（**全部 CSC**） | **0.00%** | 100% 有尖點，中位 178.9° |
| RLR / LRL（**全部 CCC**） | **100.00%** | 0% 有尖點，中位 2.2° |

整體只有 **10.73%** 的回傳路徑幾何有效，而那正好就是選中 CCC 的那些。
把容差從 1e-6 m 放寬到 1 m / 1°，有效比例**完全不變** ⇒ 這是粗差不是數值誤差。

⚠️⚠️ **先前把根因定位在 CCC（:617-619）是錯的。** CCC 幾何完全正確
（到位 1e-13、零航向不連續）；它唯一的毛病是中圓鏡像選擇固定取一邊，
在 39.66% 的案例取到較長的那一個 —— **只影響長度，不影響有效性**。
修 CCC 什麼也解決不了。

**四個獨立的真因，全部在 `_compute_csc`**：

1. **外切線（LSL/RSR）切點取到圓的正對面**，差**正好 180°**。
2. **內切線（LSR/RSL）切點差正好 90°**。
3. wrap 輔助函式在**正好相切**時把零掃掠變成一整圈 **+2πR**。
4. `acos` 定義域保護**沒有 epsilon**，把「正好相切」的內切線整個拒絕掉 ——
   而那往往正是真最佳解。

另有 `_insert_loiter`（:210）對小於 2R 的轉場固定加 2πR，且幾何上是 no-op。

**最簡反例 [驗證]**：要一條**純直線**。等航向、純沿航向位移 S，
repo 對**任何** S 都回傳 **S + 2πR**：

```
S = 1000 m  ->  repo 1813.4332 m (RSR)   真值 1000.000000
S = 5000 m  ->  repo 5813.4332 m (RSR)   真值 5000.000000
```

差值恆為 813.4332 = 2πR。⚠️ 注意 S 遠大於 2R，**沒有觸發 loiter** ——
這證明外切線分支的錯誤獨立於 loiter 存在。

**規模 [驗證]**：
* **14.34%** 的回傳長度**短於**真最佳解 ⇒ 物理上不可能，是無效路徑。
* ⚠️⚠️ **6.72% 的案例長度剛好正確但幾何無效** ⇒ **任何只比長度的測試都會放行它們**。
  這直接決定驗收判準必須包含 A1/A3（見 §8）。
* 選字被嚴重帶偏：錯誤會**減掉**一整圈，讓錯答案看起來最短。
  repo 選 LSL 38.10% / RSR 39.61%，真實最佳頻率只有 23.51% / 20.75%。

⚠️⚠️⚠️ **本 session 產出的補丁不可採用。** 提出者宣稱在自己的 36,864 組掃掠上
零失配，但驗證組在**該掃掠沒有涵蓋的姿態族**上測出「路徑到不了終點姿態，
長度不到真最佳解的一半」。⇒ 下一個 session 必須**重新設計修法並重新驗證**，
而且驗證的姿態族要由**與提出者不同的人／方法**決定。

⚠️⚠️ **本 session 提出的補丁已被驗證組推翻** —— 「產生的路徑到不了終點姿態，
長度不到真最佳解的一半，出現在該研究自己的掃掠沒有涵蓋的姿態族上」。
⇒ **下一個 session 必須重新設計修法，不可沿用**。

**影響範圍 [實測]**：把已驗證的求解器 monkeypatch 上去跑完整測試套件兩次
（一次只改長度、一次連幾何一起換），兩次結論相同：
基準 4111 passed / 227 skipped → **5 failed, 4106 passed**。只有 5 條測試會動。
原因是 **repo 裡沒有任何一條測試碰 Dubins 幾何**
（`tests/` 底下對 `generate_waypoints` / `DubinsSegment` / `angle_sweep` /
`calculate_path` / `Pose3D` 的搜尋結果全部為零）。

修好之後航線長度**變短**：8 個 DCCPP 情境的 makespan −0.13% ~ −4.12%（中位 ≈ −2.0%）。
⚠️ 但真正重要的不是長度：**8 個情境裡有 7 個「哪些條帶分給哪一台」會改變**。

### B2. 混編隊在輸入端表達不出來

**[實測]** `ui/main_window.py:5193-5205` 把**同一組** speed / turn_radius /
fov_width / vehicle_type 複製 N 份給每一台。在選任何分配目標之前，
per-aircraft 的輸入通道必須先存在。

### B3. 速度沒有傳進求解器 ⇒ 目標退化

**[實測]** `mission/swarm_coordinator.py:1228-1233` 建 `uav_inputs` 時
**沒有 `'speed'` key**，而 `core/dccpp/idp_solver.py:219` 用 `max(..., 1e-6)`，
全隊同一個除數 ⇒ min-max **時間**在數學上退化成 min-max **距離**。

實跑驗證：不給 speed → 兩台各 {12, 12} 條掃描線；給 21.5/19.0 → **{13, 11}**。
現況實測 Pioneer 16299.2 m、HERO 16252.5 m（差 0.3%，等距離）。
代價：makespan 由 HERO 決定，Pioneer 空等 **97.3 s（11.4%）**，任務長 **6.43%**。

⭐ `val = total / sp` 在 `idp_solver.py:312/:429` **已經寫好了**，差一個 dict key。

⚠️ 另外：UI 顯示的 makespan **是秒**（`estimate_flight_time_s`），
但最佳化器從來沒有最小化過它 —— 目標與報表不一致，只在速度不同時現形。

### B4. HERO 的巡航空速輸不進去

**[實測]** `ui/widgets/vtol_recon_panel.py:364` 是 `setRange(20.0, 34.0)`，
下限寫死 20，因為 `sitl/default_params/vtol_default.parm` 的 `AIRSPEED_MIN=20`
是**單一全域值**。HERO 巡航 19.0 低於它，兩台的最低空速（18/16）也都低於它。
⇒ `AIRSPEED_MIN` 必須變成逐機，並隨機體寫進各自的 `.parm`。
鎖在 `tests/test_airframe.py::test_known_airspeed_floor_trap`，改好會變紅。

### C2. 過渡段 **[實測，TRIAL VTOLTC1]**

SITL 三趟受控實驗，資料在 `runs/artifacts/VTOLTC1/`。

* `Q_TRANSITION_MS` 管的是**前向**（MC→FW），且**精確**：3000→9000 讓前向多 6.00 s。
  ⚠️ `vtol_default.parm` 的方向註解**寫反了**；`vtol_profile.py` 才是對的。
* ⚠️⚠️ `Q_BACKTRANS_MS` **管不到**降落的反向過渡：參數變 4 倍，耗時只變 5%。
  降落減速由進場幾何與 `Q_TRANS_DECEL` 決定。
* 前向過渡實測 **7.85 s / 120.7 m**，而模型只給 36 m（**3.35×**）。
  真因：`Q_TRANSITION_MS` 只是**達到最低空速之後**的計時段（3.0 s），
  前面還有 **4.90 s** 在把空速從 0.5 加到 20.2，模型完全沒算。
* 兩段過渡**都在爬升**：前向 +4.0 m、反向 **+12.1 m**。模型都當平飛。
* ✅ `Q_PILOT_SPD_UP=2.5` 實測 **2.52**，吻合。

⚠️ VTOLTC1 是在巡航 24 / 最低 20 的 SITL 組態下飛的。加速段同時取決於目標空速
與推重比，而 Pioneer 24.6 kg 對 HERO 6.65 kg 是 3.7 倍質量差
⇒ **這些數值不能直接套到兩台實機**，只有結構（加速段＋計時段、兩段都爬升）可沿用。

⚠️ **[未驗]** `TECS_CLMB_MAX` 尚未實測。VTOLTC1 那趟固定翼段爬升率中位 0.72 m/s，
但航段長 3.3 km、需求梯度遠低於能力上限，**沒有觸頂** ⇒ 不可拿來反駁 5.0。

### C3. 轉彎半徑與條帶間距 **[推導]**

來回掃描時，條帶間距 `s < 2R` 就必須飛出作業區才轉得回來。
Pioneer 需 `s ≥ 320 m`（設計半徑）或 259 m（理論）；HERO 需 200 m 或 158 m。
⚠️ 這個門檻由**感測器掃幅**決定，不是由飛機決定。缺掃幅資料就無法判定
兩台在同一個間距下誰能飛乾淨的轉彎。

## 7. 分配目標：三個答案差十個百分點 **[實測]**

| 綁定的約束 | Pioneer : HERO |
|---|---|
| makespan（速度） | 53.1 : 46.9 |
| 續航 | 56.4 : 43.6 |
| **航程** | **62.7 : 37.3** |

航程是真正付錢的那個：平均分配把機隊上限壓到 158.4 km，而可用是 212.3 km。

⚠️ **「Pioneer 多分」有兩個可計算的反例**：

1. 一旦改成逐機轉彎半徑，在 min-max **距離**下 **HERO 該拿更多**
   （12.195 對 11.805 條）。轉場開銷下限是 **π·R**，差距 π(160−100) = **188.5 m/次反向**。
2. **面積**交付上，HERO 掃幅超過 Pioneer 的 **1.68×** 就該多分。
   ⭐ 注意掃幅在**距離**分割裡**完全消掉**（比值恆為 1.6806，掃幅比 0.5→3.0 都一樣），
   它只移動**面積**分割。

❌ **「按形狀分配」已被否決 [實測]**。主控變數是**掃描線長度 L**，不是大小或開闊度：
`η_P/η_H → (L+πR_H)/(L+πR_P)`。而 `find_min_width()` 把掃描線鋪在長軸，
同一區的兩台**共用同一個 L**，只有 W 不同 —— W 正是比值最不敏感的那一維。
形狀項只在 5.6–10% 的區塊配對上改變決定，買到中位 0.82–1.37% 的任務時間。不值得做。

⭐ 真正決定的是**航程，而且是硬可行性切割不是偏好**：
HERO 連從 home 出發都飛不完一個 3000×3000 m 的區（需 99.4 km／預算 79.2 km）
⇒「HERO 拿近的小區」本來就被強制，不必另外寫規則。

## 8. 驗收判準

不要用「看起來比較合理」。每一條都要值層級可量。

| # | 判準 | 量法 |
|---|---|---|
| A1 | Dubins 回傳的路徑必須**到得了終點姿態**（<1e-6 m / 1e-9 rad） | 前向積分它自己回傳的段 |
| A2 | Dubins 長度**永遠不得短於**真最佳解 | 對照獨立驗證過的求解器 |
| A3 | 路徑**無尖點**：相鄰航點方向變化 < 1° | 逐點量 |
| A3b | ⚠️ **A1 與 A3 不可省。** 實測 **6.72%** 的案例長度**剛好正確**但幾何無效 ⇒ 只比長度的測試會全部放行 | — |
| A4 | 兩台的**時間** makespan 差 < 5% | 逐機距離 ÷ 逐機速度 |
| A5 | 任一台的任務總長 ≤ 該機 `usable_range_km` | 含返航段 |
| A6 | 每台實際飛的轉彎半徑 = 該機的設計半徑，不是全隊 max | 量最小轉彎曲率 |
| A7 | 覆蓋率驗算對兩台用**各自**的掃幅 | 現況 `coverage_verifier` 只吃一個純量 |

⚠️ **對照組必要**：改動前後都要跑同一組情境，並比對「哪些條帶分給哪一台」，
不是只比總長度 —— 修好 Dubins 之後 8 個情境有 7 個的分配會變。

## 9. 這個 session 踩過的陷阱（不要重踩）

1. **`Pose3D.heading_deg` 的 0 度是「東」不是「北」。** 我用錯幾何量了一次
   Dubins，得到「錯 1.90×」的假結論。真正的側向 2R 案例 repo 其實是**對的**
   （406.72 = π·R）；錯的是小於 2R 與大於 3R 兩個區間。
   ⚠️ 而且方向也搞反了：那個姿態對的真最佳解是 **2πR = 813.43**，
   repo 的 772.89 是它的 **0.95 倍 —— 太短，不是太長**。
   「太短」比「太長」嚴重：長度短於 Dubins 最佳解代表那條路徑根本連不起來。
   ⇒ 用錯的錨點寫測試，會鎖住一個假的期望值。
1b. **同一個姿態對上，`d=258.9` 與 `2R=258.9238` 跨在 loiter 分支的兩側**，
   兩個引用數字（772.89 與 1586.31）其實來自不同分支。
   量測點貼著分支邊界時，要先確認自己落在哪一邊。
2. **參考解自己也會有 bug。** 我的 `LRL` 閉式寫錯，前向積分驗證擋掉了，
   所以沒給錯答案，但**有盲點**（鏡像側回報 1021 m，真值 870）。
   用鏡像對稱（L↔R）補掉，不要再猜第二次公式。
3. **小角度下 `sin ≈ tan`。** 3° 時只差 0.14%，容差 5e-3 就驗不出公式寫錯。
   要另加一條陡角測試。
4. **斷言字串會互相包含。** 兩條錯誤訊息都含「失速」，拿掉其中一個檢查後
   `match="失速"` 照樣通過。要挑各自獨有的片段。
5. **子代理的突變實驗會就地改寫工作樹。** 這個 session 有一次把
   `main_window.py` 的兩個轉換函式在 import 時互相改名留在樹上，
   而當時 65 條測試**全綠**（它們鎖的是函式本身，不是呼叫端綁哪一個）。
   ⇒ 跑分析型 workflow 要明文禁止改檔，並在事後 `git diff` 檢查。
6. **Bash heredoc 會吃掉一級逃脫。** 寫含 regex 的測試檔用 Write 工具。
