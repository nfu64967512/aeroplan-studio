# 3D 畫面 60 FPS（「希望 3D 畫面可以像 X-Plane 一樣順暢」）— 2026-10-17～19

使用者要求：3D 畫面要像 X-Plane 一樣順。前一輪（`docs/實作_2026-10-17_多機效能.md`）把遙測、合幀、插值都做了，
但 3D 卡在 ~22 FPS。這一輪拆開量，找到兩件事：(1) 一個**環境觸發**的 22 FPS 上限（10-17 穩定出現、10-19 消失），
用 Qt 呈現設定解掉；(2) CAD 模型每架上千個 draw call，用模型合併解掉——這個才是多機時穩定有效的修正。
另外修了追機鏡頭的三個舊洞。審查（對抗式，21 條、推翻 3 條）後已依結果修正與重量。

本機 vtol 分支、未 commit。量測全部在 `runs/artifacts/PERF_2026-10-17/`（`fps_probe.json`、`x_plane_*.csv`）。

### 1.2 22 FPS 上限是環境觸發的（2026-10-17 有、10-19 沒有）

- 10-17：連一個用 rAF 移動的 div 都只有 21.8 FPS，幾十次量測都一樣；swapInterval 0 一律變成 60（見 §2）。
  那天 profiler 的 VTOL 改前 21.3–22.0、改後 60.0–60.2（但樁機在畫面外，只量到呈現這一項，審查抓到）。
- 10-19：同一台機器、同樣的舊設定（swapInterval 1），同一個 div 頁 60.2 FPS、Cesium 空場景 60.0 FPS ⇒ 上限沒有出現。
  這天系統計時器解析度是 1.0 ms（被其他執行中的程式調高；`NtQueryTimerResolution`）。
- 10-17 的幀間隔正好是 Windows 預設計時器刻度 15.625 ms 的 3 倍／2 倍 ⇒ **推論**（未驗證）：系統計時器停在 15.6 ms 預設時

- swapInterval 0 保留：上限出現時它能解（10-17 實證），不出現時沒有差別也沒有副作用（10-19 實證）。

## 2. 22 FPS 上限（10-17 出現時）與 Qt 呈現設定

拆法（每組一個行程、依序跑，GPU 量測不並行）：

- 連「一個用 rAF 移動的 div」、2D canvas、只清色的 WebGL 頁，在 `QWebEngineView` 裡也全是 **21.8 FPS**、幀間隔集中在 47 ms
  （Qt 端 `afterRendering` 計數也一樣）⇒ 不是 Cesium、不是架數。
- 畫布大小（929×589 vs 700×450，畫素差 1.74 倍；探針的 `--size` 是視窗、150% 縮放下畫布比較小）、app 的 GPU 旗標有無、
  探針行程的 `timeBeginPeriod(1)`、`QT_D3D_MAX_FRAME_LATENCY`=0/1/3、`QSG_RHI_BACKEND=d3d11`：全都不變。
  `--disable-gpu-vsync --disable-frame-rate-limit`：頁面空轉到 1200 FPS，但 Qt 端照樣 22。
- 空白頁只跑 rAF（不出新畫面）是 60 Hz（第一版探針把 rAF 數了兩次、記成 120，審查抓到已修）⇒ BeginFrame 本身不慢，
  慢在「有新畫面要交給 Qt」的那一段。
- `QSurfaceFormat` 預設 **swapInterval = 0** ⇒ 同一頁 **60.0 FPS**（Qt 端也 60.0）。

解讀：`QWebEngineView` 內部是 `QQuickWidget`，整個頂層視窗改走 RHI（D3D11）交換鏈；swapInterval 0 讓 Qt 端 present 不等 vsync，
出圖節奏交給 Chromium 自己的 60 Hz BeginFrame。⚠ **確切機制沒有查明**：swapInterval 1 時的幀間隔集中在 46.9 ms、次峰 31.25 ms，
正好是 Windows 預設計時器刻度 15.625 ms 的 3 倍／2 倍，**不是** vsync 的倍數（50.0／33.4 ms，量到 0 筆）⇒ 比較像「present 的等待
加上某處用粗計時器輪詢」，不是單純「每幀等三個 vsync」（第一版文件這樣寫，審查用直方圖推翻）。`timeBeginPeriod(1)` 只影響探針自己的行程，
QtWebEngine 的 renderer 行程不受影響，所以那組對照不能排除計時器假說。只在這台 60 Hz 螢幕量過，高更新率螢幕是否仍上限 60 沒驗。

被否決的路（FPS 數字會騙人，一定要截圖看；探針 `--shot` 抓的是桌面那一塊，GL/D3D 視窗直接 `grabWindow(winId)` 會是白的）：

- `QSG_RHI_BACKEND=opengl`：60 FPS，但**畫面全白**（Chromium 的 D3D 貼圖進不了 GL）。
- `QT_D3D_NO_FLIP=1`＋swapInterval 0（舊式 blt 交換鏈，本來想用它避開 ALLOW_TEARING 撕裂）：60 FPS，但**畫面同樣全白**。
- `QSG_RHI_BACKEND=d3d12`：44.6 FPS、幀間隔兩極（7 ms／36–41 ms），沒再追。

修法：`ui/render_setup.py::configure_qt_presentation()`，`main.py::run_gui_mode` 在 `QApplication` 建立前呼叫。
Windows 預設 0，其他平台不動；環境變數 `AEROPLAN_QT_SWAP_INTERVAL`（`1` = 舊行為、`default` = 不動 Qt 預設）。

## 3. CAD 匯出的模型每架上千個 draw call（穩定有效的修正）

CDP CPU profile（`QTWEBENGINE_REMOTE_DEBUGGING` ＋ raw websocket，Playwright 的 `connect_over_cdp` 連不上 QtWebEngine）：
6 架時 92% 在 Cesium `render`，其中 draw／`_setUniforms`／`bindVertexArray`／Model 更新佔大宗；我們自己的 JS（`updateUAVPositions`）不到 1%。

| 模型（gitignored 本機資產） | primitive | 三角形 | 材質 |
|---|---|---|---|
| `ui/resources/vtol.glb`（THREE.GLTFExporter） | **1192** | 103 萬 | 51 個，**全都沒有 baseColorFactor**（畫出來同一種白） |
| `ui/resources/copter.glb` | **383** | 112 萬 | 20 個，同上 |
| `ui/resources/barracuda500.glb` | 3 | 34 萬 | 3 個 |

Cesium 每個 primitive 一次 draw call ⇒ 6 架 VTOL 每幀 ~7000 次。GPU 畫三角形不是瓶頸（空場景 1200 FPS），draw call 數才是。

修法：`ui/widgets/glb_merge.py`（純 numpy，不加套件）

- 節點變換烘進頂點（matrix／TRS、法向量用逆轉置再正規化、行列式 < 0 反轉三角形頂點順序）。
- 依「外觀簽名」（材質去掉 name/extras）分組，每組一個 primitive；同一節點裡共用同一份 POSITION/NORMAL 的 primitive 頂點只放一次
  （第一版沒做這件事，vtol 從 100 MB 膨脹成 416 MB）。
- 有貼圖、非三角形、sparse、外部 buffer、必要擴充、骨架／動畫 ⇒ 回 None，用原檔。
- 結果：vtol 1192 → **1** 個 primitive（100 → 86 MB，0.5 s），copter 383 → **1**（114 → 94 MB），barracuda 不動（< 8 個不合併）。
  三角形數、座標、法向量、材質參數都不變；main.html 的比例／朝向校正不用改。
- `optimized_model_path()`：快取在 `data/cache/models/<名>.merged-<鍵>.glb`（gitignored），鍵 = 原檔大小 + mtime + 演算法版本；
  原子寫入、舊快取刪掉、任何失敗都退回原檔。`CesiumMapWidget._cesium_template_values` 三個模型都走它。
  環境變數 `AEROPLAN_GLB_MERGE=0` 關掉（對照用）。第一次開 3D 會花 ~1 s 做兩個檔，之後直接用快取。
- 兩個 conftest 預設 `AEROPLAN_GLB_MERGE=0`：建 CesiumMapWidget 的測試不可以把 180 MB 的快取寫進 repo。

## 4. 追機鏡頭（像飛行模擬器的 chase view）

`main.html::_chaseSmoothYaw`：鏡頭偏航一階低通（α = 1 − e^(−dt/τ)，與幀率無關、走最短角、dt 上限 0.5 s），τ = `smoothing × 2`
（預設 0.18 ⇒ 0.36 s；這個參數以前存在但從沒用到）。位置不阻尼，飛機永遠在畫面同一處；17°/s 的轉彎鏡頭穩態落後約 6°，
也濾掉遙測航向的小抖動。`setChaseCamera`／`resetChaseView` 都會讓下一幀直接對齊機頭；`smoothing=0` = 舊的剛性鎖機頭。

審查抓到、已修的舊洞（真 Cesium 重現後修）：
- **飛到某點後鏡頭跑到 6,375 km 外**：`flyToPos` 完成、`setViewPos` 都會把相機座標系換回世界座標，追機下一幀把 ECEF 座標當成偏移照抄。
  匯入多檔航點、場地預設、找平坦位置都會呼叫到。⇒ 偵測相機座標系被換就從後方視角重新對齊；追機時取消相機飛行
  （否則飛行途中 3 s 會被慢慢帶走到 557 m）。
- **閒置也一直算圖**：阻尼指數逼近永遠在改相機（剛性鎖也每幀浮點抖一個 ULP）。⇒ 差距 < 1e-5 rad 直接對齊、
  座標系與偏移都沒變就不呼叫 `lookAtTransform`。
- **俯角參數沒人讀**：四個預設（-8／-10／-15／-20°）其實全是 14°。⇒ 高度 = 水平距離 × tan(|俯角|)。

## 7. 限制與後續

- swapInterval 0 時 Qt 的 D3D11 flip 交換鏈會帶 ALLOW_TEARING（qtbase `qrhid3d11.cpp`：`swapInterval == 0 && supportsAllowTearing`；
  這台機器 log 顯示支援）。一般視窗由 DWM 合成不會撕裂；視窗被系統升格成獨立翻頁（全螢幕、或 MPO 硬體疊加層）時**可能**出現撕裂線。
  截圖驗不出撕裂，這點**沒有驗證**，要人眼在最大化／全螢幕下看。能避開它的舊式交換鏈畫面是白的（見 §2），
  所以真的撕裂時只能設 `AEROPLAN_QT_SWAP_INTERVAL=1` 回到舊行為（上限出現的那種環境下會回到 22 FPS）。
- 22 FPS 上限的觸發條件只是推論（系統計時器 15.6 ms 預設），沒有辦法在這台機器上主動重現來驗證。
- 合併後每架仍是 100 萬三角形；RTX 4070 綽綽有餘，較弱的顯卡可能變成 GPU 瓶頸 ⇒ 之後可以加減面（LOD）。
- vtol.glb／copter.glb 的材質顏色從匯出時就遺失（名字是 Opaque(r,g,b) 但沒有 baseColorFactor），合併刻意保持原樣不改外觀。
- 2D 地圖同樣受惠於 swapInterval 0（同一個 Qt 呈現路徑），但這輪沒有另外量 2D 的 FPS。
