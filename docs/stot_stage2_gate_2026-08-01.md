## 1. 機制:閘門自己造出來的極限環

裸比較 `alt < cruise_alt_threshold` 在三個地方各自算一次,每次翻轉同時做三件破壞性的事:

1. **速度指令從追趕 157 EAS 掉回 best_climb 96 EAS** —— 縱向唯一有權限的通道當場關掉。
2. **側向展開角瞬間塌回 0°** —— rank2 的側偏是 ±4589 m,slot 橫向跳 4.6 km,
   再用 `expand_time_s`(120 s)重新展開。下一次下沉在 5–40 s 後就來,**永遠展不完**。
3. **`bearing_off` 被強制收成 180°**(純 trail),橫向站位放棄。

於是:飛機為了追趕而拿高度換速度 → 下沉觸發閘門 → 閘門砍掉追趕速度 → 爬回高度
→ 再加速 → 再下沉。巡航窗口從 168 s 拉到 630 s 末端誤差不會變好(P61 vs P71),
正是因為時間都花在這個循環裡。

巡航高度 3100 m、閘門 3000 m,**餘裕只有 100 m**,而追趕中的飛機本來就會拿高度換速度
⇒ 沒有遲滯就必然抖動。

### 佐證:誤差是橫向的

`stot_stage2_report.py` 把誤差分解成沿航向/垂直航向。P91 的 UAV5:

```
 uav   err_end     along     cross
   5     35630    -12176    +33485
```

**+33.5 km 是橫向**。橫向偏置正是閘門翻轉會打掉的那一項 —— 機制與症狀對得上。
(若真是「重發被跳過」造成的開迴路直飛,誤差應該以沿航向為主。)

## 2. 修法

新檔 `sar_swarm_patches/phase_gate.py`,兩個無 ROS 依賴、可單元測試的元件:

### `LatchedAltGate` —— 遲滯 + 最短駐留

- **進入**巡航段:`alt >= threshold`,第一次到達就算數(不帶遲滯)。
- **退出**:要同時滿足 (1) `alt < threshold − hysteresis`、(2) 連續 `dwell` 秒。
- 預設 `hysteresis=150 m`、`dwell=5 s` ⇒ 退出線 2850 m。

餘裕檢查:P91 的 UAV5 重放後最低點是 **2911 m**,比退出線高 61 m ⇒ 那些抖動全部被吃掉;
但真的掉高度(連續 5 s 低於 2850)仍然會誠實地退回爬升段。

⚠️ 相位改成**每個 `_fly` tick 只算一次**的 latch,四個消費者(展開角、`bearing_off`、
速度、cmdlog 標籤)一律讀 `self._climbing`。三處各自裸比較會在同一 tick 內看到不同相位。

### `MonotonicRamp` —— 側向展開只增不減

原本用起算時刻 `_expand_t0`,一回到爬升段就歸零 ⇒ 展開角塌回 0°。
改成累積器:巡航段累積、爬升段**凍結**。就算遲滯被真實的掉高度突破,
slot 也只是停在原地等,不會橫向瞬移 4.6 km。

程式碼本來就有「不可以在門檻上硬切換」的註解,但只防了「往上展開」那一邊。

### 驗證

- `tests/test_phase_gate.py`:19 項,含用 P91 實際下沉深度重放的正反證
  (`hyst=0/dwell=0` 翻 21 次 → `hyst=150/dwell=5` 翻 1 次)。
- 全套 207 項通過。
- 實跑 T1:四架僚機 **相位翻轉 0 次**(P91 的 UAV5 是 20 次)、身後航點 0.0–0.3%、
  UAV5 **一次乾淨的斜坡展到滿角 35°**(展開日誌 18 行);P91 是 54 行、反覆重啟、從未展完。

**閘門的修法本身完全達到設計目的。但階段 2 仍未通過** —— 見下一節。

## 2.5 階段 2 仍未通過 —— 但下一個瓶頸已經定位

|---|---|---|

是唯一沒被拖垮的。

⚠️ **P91 的 4/5 架「收到 1400–1600 m」其實也不是收斂**,只是當時僚機比長機**快**
10–18 m/s,誤差才沒有跑掉。兩趟的僚機速度差了一倍,**任何跨這兩趟的比較都不成立**。

已修:爬完之後補送 `DO_CHANGE_SPEED CLIMB_DONE_V`(= 巡航 135 EAS),
交棒的狀態直接就是巡航狀態。**尚未驗證**(U1 航次進行中)。

⚠️ 還沒解釋的:為什麼 `wingman_node` 每 3 s 送一次 157 EAS 卻改不動它。
速度指令走 MAVROS `CommandLong`,爬升區塊走**直連飛控**;

## 4.5 U1:速度交棒修好之後,下一層瓶頸是**能量**

U1(= T1 + 爬完把速度交棒回 135 EAS):

| | T1 | U1 |
|---|---|---|
| 僚機地速 | 84–95 | **104–111** |
| 僚機 `cmd_speed_eas` 中位數 | 157 | 96(= best_climb,因為掉回爬升段) |
| 僚機高度中位數 | 3091–3221 | **2138–2970**(最低 1523) |
| 長機高度中位數 | 3133 | **4601** |
| 閘門退回次數 | 0 | 1–4 |

速度確實拉起來了,但**高度換掉了** —— 僚機從 3100 m 掉到 2100 m,
`<2850 m` 的時間佔比 28–93%。閘門於是誠實地退回爬升段(這正是遲滯該有的行為:
1000 m 的下沉不是抖動,是真的掉高度),把速度收回 96 EAS。

⇒ **這台機體在 3100 m 沒有同時維持「巡航速度 + 巡航高度 + 追 4–8 km 外的側向 slot」的能量。**
`THR_MAX` 這一趟其實還停在助推值 35(`CRUISE_THR_MAX` 沒設 ⇒ 收回那段沒觸發),
也就是說**推力比設計值還多**,仍然不夠。

另外發現長機爬到 **4601 m** = `CRUISE_ALT 3100 + SHOW_VERT_DZ_MAX 1500`:
`SHOW_VERT_COORD` 預設是**開的**,而垂直通道協同早就被受控實測推翻
(抵扇形散布 119.0 vs 關閉 14.1 s)。P91 之所以沒踩到,只是因為僚機夠近、
`lag` 沒超過門檻 —— **已推翻的東西不該靠「剛好沒觸發」來避開**。
`run_west.sh` 已顯式關掉。

### ⭐ U1 的關鍵證據:UAV6 收斂到 560 m,其餘四架發散到 ~100 km

| uav | slot 側向偏置 | err_end | err_min | 趨勢 |
|---|---|---|---|---|
| 2 (rank1) | ±2294 m | 102477 | 3252 | 發散 |
| 3 (rank2) | ±4589 m | 97084 | 5382 | 發散 |
| 4 (rank1) | ±2294 m | 98913 | 1524 | 發散 |
| 5 (rank2) | ±4589 m | 81066 | 605 | 發散 |
| **6 (V尾)** | **0** | **560** | **10** | **收斂** |

UAV6 用**同一具機體、同一段空域、同一個速度權限**,唯一的差別是
**它的 slot 沒有側向偏置**(`bearing_off = 180°`)。它收斂到 560 m,
最近時只差 **10 m** —— 遠在 200 m 門檻之內。

⇒ 瓶頸在**側向通道的能量成本**,不在導引律、不在閘門、不在投影點。

這個機制在爬升段已經被實測證實過一次(`wingman_node` 的註解:
側向偏置越大的機爬得越差,順序完全吻合)——現在它在巡航段重演,
只是這次代價是掉 1000 m 高度而不是掉爬升率。

## 4.8 ⭐⭐ 追趕通道從來沒有生效過(V1 用回應檢驗量到的)

加了 `DO_CHANGE_SPEED` 的**回應檢驗**之後,第一趟就抓到:

```
MAVROS 拒收 DO_CHANGE_SPEED(success=False MAV_RESULT=4);目標 157 EAS
```

六機全部,每一發。根因在 ArduPlane `commands_logic.cpp::do_change_speed()`:

```cpp
} else if ((speed_target_ms >= aparm.airspeed_min.get()) &&
           (speed_target_ms <= aparm.airspeed_max.get()))  {
    new_airspeed_cm = speed_target_ms * 100;   // 只有落在區間內才吃
    return true;
}
break;          // 區間外 → return false → MAV_RESULT_FAILED(4),整發丟掉
```

實測飛控參數:`AIRSPEED_MAX = 150`,而 `catch_speed = 157`。

⇒ **`catch_speed` 超出區間 ⇒ 每一發追趕指令都被整個丟掉(不是夾住,是不執行)。**
僚機只吃得到 `nominal` 135(≤150 才被接受)。也就是說
「落後就加速追」—— 縱向**唯一**有權限的通道 —— **從專案開始就是關的**,
而且完全靜默:指令記錄器照樣寫 `cmd_speed_eas=157`,因為那是我們送出去的值,
不是飛控接受的值。

⚠️ 兩條鏈路都一樣。這種拒收發生在**飛控裡**,不是傳輸層 ——
所以「改走直連鏈路」不能解決它(直連只是讓指令送得到,不是讓它被接受)。

### ⚠️ 更正:`DO_CHANGE_SPEED` 有**三種**互相獨立的失敗原因

第一版把所有拒收都歸給速度區間,**那是錯的**。W1(區間已放寬到 220)仍然拒收,
而且目標是 96 EAS —— 明明在區間內。查原始碼才發現還有第二道閘:

```cpp
// GCS_MAVLink_Plane.cpp::handle_command_DO_CHANGE_SPEED —— 在 do_change_speed 之前
if ((!plane.control_mode->is_guided_mode()) &&
    (plane.control_mode != &plane.mode_auto)) {
    return MAV_RESULT_FAILED;          // 不在 GUIDED/AUTO 就整發拒收
}
```

| # | 原因 | 徵狀 | 實測 |
|---|---|---|---|
| 1 | 目標不在 `[AIRSPEED_MIN, AIRSPEED_MAX]` | `MAV_RESULT=4` | V1:catch 157 > max 150 |
| 2 | **飛機不在 GUIDED / AUTO** | `MAV_RESULT=4` | W1:目標 96 在區間內仍被拒 |
| 3 | MAVROS 收不到 `COMMAND_ACK` | `success=False` 但 **`MAV_RESULT=0`**(欄位沒填) | V1/W1 都有,是**傳輸層** |

⇒ 只有 (3) 是「MAVROS 斷鏈」;(1)(2) 是飛控主動拒絕,換鏈路沒有用。
WARN 已改成**一併印出目前飛行模式**,讓日誌自己區分是哪一種。

**這很可能解釋了歷次航次「速度指令正常、max-consensus 正常、閉合率算得出來,
但誤差就是收不掉」的整類現象。**

已修:
- `AIRSPEED_MAX_CAP` 150 → **220**(這個參數的原意就是「解除上限」,150 反而綁住了指令)
- `wingman_node` 送出前**夾到 `[airspeed_min, airspeed_max]`** 並 WARN
  —— 寧可拿到上限值,也不要因為超界而讓整發被丟掉、停在上一次的舊值
- 開機時若 `catch_speed > airspeed_max` 直接 `ERROR`,不要等航次跑完才發現

⚠️ **因果要修正**:正橫航點是**發散的結果**,不是原因。
先前假設「正橫 → 極限坡度 → 誘導阻力 → 掉高度」,但實際順序是
「能量/速度權限不足 → 站不住 slot → 誤差長大 → slot 跑到正橫」。
L1 是對的改動(近場更平滑),但它不是階段 2 的解藥。

## 4.9 X1:側偏凍結自己製造了身後航點(已修)

X1(= V1 + `AIRSPEED_MAX_CAP` 165)。階段 1 **恢復正常**(`全員抵巡航高度` 有印),
但階段 2 是歷來最差,而 `behind%` 從先前的 0.0–6.6% 爆到 **19–74%**。

分相位一拆就清楚了:

| 相位 | \|brg\|中位數 | behind% | d2wp 中位數 |
|---|---|---|---|
| CLIMB(凍結生效) | **112°** | **99.8–100%** | **1499 m** |
| CRUISE | 83° | 0.0% | 4012 m |

**距離剛好等於 L1(1499),方向卻整個錯掉。** 原因是側偏凍結把目標放在
「沿**長機**航向往前 L1」—— 那只保證它在**長機**前方;本機掉高度時常常正在轉,
指向和長機差 112°,目標就落在自己身後。而我在凍結分支 `return` 得太早,
把既有的「航點永遠不可以落在飛機後方」保護整個跳過了。
再配上 15° 坡度上限(轉彎半徑 9.4 km)轉不回來 ⇒ UAV4 末端誤差 **112 km**。

已修:新增共用的 `_ahead_of_nose()`,**橫向照留、縱向夾到機頭前方 ≥ `trail_ahead_m`**
(不是整個改投影到機頭指向 —— 那是 P81 那個更糟的失敗:誤差 10573 → 28018 m)。
回歸測試 `tests/test_lookahead_geometry.py::TestFreezeTargetMustBeAheadOfNose`
用 X1 的實際夾角(112°)把這個 bug 釘住,含「橫向分量不可被改掉」那一條。

⚠️ 教訓:**既有程式碼裡反覆出現的鐵律,通常是用實測換來的。** 這個專案的
「航點永遠不可以落在飛機後方」已經被三趟航次寫進註解,而我加新分支時
繞過了它 —— 而且症狀是「距離對、方向錯」,不看分相位的統計根本看不出來。

### ⚠️ 已知瑕疵(尚未修,避免一次動兩個變數)

`_v_target` 的**投影分支**(trail 投影、側偏凍結)都是
`self._ff_target = None; return 投影點` —— 於是 `_formation_control` 量到的
`err` 是「對投影點」的距離,不是對真 slot 的。投影點固定在前方 ~1500 m,
所以**凍結期間回報的誤差會被壓成 ~1500 m**,比真實誤差小;
`speed_for_error` 與 master 的 max-consensus 都吃這個值,長機會因此
「以為僚機快到了」而不等。

正解是照架構的原意分離:`_ff_target = 投影點`(導引用)、`return 真 slot`(量誤差用)
—— 主分支本來就是這樣寫的,只有投影分支沒跟上。
**等閘門/速度權限的對照數字乾淨了再改**,不要和這一輪混在一起。

`master_node.py` 的 `master_alt_gate` 有同樣的裸比較,但它**預設關閉且應該維持關閉**
(受控實測:爬升段關掉 max-consensus 讓散布從 62.7 s 惡化到 188.2 s)。
已加註解:若哪天要重新啟用,改用 `LatchedAltGate`,不要用裸比較。
