# HV4SITL13 — 全隊起飛時刻全域重排（vendored 修改 #3）首航

2026-09-08 · ArduPlane 4.8.0-dev QuadPlane SITL ×4 · speedup 5 · 分支 `quad_swarm`
情境 `gui_legal_120_split_resched` · 埠 6760–6790

## 這一趟在測什麼

與 **HV4SITL9 逐欄相同**的幾何、機隊與空域（一大區 1560×800 m 自動切 4、
1 Pioneer + 3 HERO、法規 120 m AGL 無豁免、min_fw 100/100、高度帶下限 15、
目標 GSD 0.05）。規劃器唯一的差別是 `PlannerConfig.global_reschedule`
⇒ **這是一次乾淨的 A/B**。

## 為什麼要做這件事

HV4SITL9 的 makespan 1799.8 s 裡，**起飛錯開跨距就佔 1265.6 s（70.3%）**。
追下去發現那不是起飛的問題：`takeoff_schedule` 本身只產生 180 s 跨距，
撐到 1265.6 s 的是 `deconflict.repair()`，而驅動它的 **6 筆衝突全部**是
同一個場坪 H 的**降落**走廊排隊（`kind='corridor'`、`res_kinds=('landing','landing')`、
d_h = d_v = **0.0**）—— 沒有一筆是空間衝突。**起飛被押後，是為了解 500 s 後
才發生的降落坪衝突**，而修復是逐衝突貪婪、工期壓縮又一次只平移一機
⇒「A 晚一點起飛好讓 B 早很多」這種協同平移結構上做不到。

## ⚠⚠ 代價：最小間距少了 37%

239.5 → 150.8 m（規劃值 148.4 m）。門檻 `d_sep_m = 100 m`，所以仍然合規，
規劃 `validate` 也是 conflicts=0。但餘裕從門檻的 2.4 倍縮到 **1.5 倍**。

⚠⚠⚠ **而量這件事的儀表本身在這個尺度上不可靠**：`flight.csv` 取樣 **5 s**，
兩個相鄰紀錄點之間 HERO 走 95 m、Pioneer 走 108 m。
`separation_from_tracks.json` 是在那之間內插（`step_s: 2.0`），檔案自己的 caveat
也寫「這是上界」。**再往下壓間距之前，遙測取樣必須先加密到 ≥2 Hz**，
否則「實飛沒違規」是假綠燈。

六對裡有三對（A1-B2、A1-B4、B2-B3）**從未同時在空中**，所以只有三對真的量得到。

## ⚠ 平移不具不變性（不可以忽略的機制細節）

4D 判準是 `|t_a − t_b| < Δt + σ_a + σ_b`，而
`σ_t = min(k_t·(t − t_sync), SIGMA_T_MAX_S)` 是**絕對時間**的函數。
全隊同步平移（相對時距一格沒動）實測 Δ=+300 s 就會多出 1 筆衝突。
⇒ **提早起飛帶來的改善有一部分來自 σ 變小**（模型餘裕），不是純排程壓縮。
單獨把 `k_t` 設 0 也能拿到 −304.6 s，量級相當。上面那個 −37% 的間距縮減
與這件事是同一枚硬幣的兩面。

## 這一趟沒有證明的事

* **三台同時在空中仍然是 0 秒**。天花板是單一場坪的降落走廊。
  下一個槓桿是**第二個起降場坪**（離線估計邊際 −451.2 s，比重排還大），
  但需要真正接上 `UAVInstance.start_site_id`（轉接層目前 0 命中），
  而且 `planner.append_rtb` 選降落站**只看能量、完全不看走廊忙碌**
  （實測給 8 個備降點，四機照樣全落 H）。
* 過度覆蓋 2.623× **沒有改善**，因為這一項只動時間不動幾何。
  「不跑重複的路徑」那一半要另外做（四條 ~1.4 km 空腿、起降場位置、接縫側疊）。
* 覆蓋率是**上界**（航跡 + 138.6 m 刈幅緩衝，未計 `sensor_on`）。
* 機體物理是 SITL 內建 `quadplane` 模型。
