## 一、量到的基準:規劃是準的,轉彎不是規劃想的那樣

### 1.1 航跡長度:規劃與實飛差 1.3–1.5%

逐段對齊(每個導航項 k:規劃腿 = 前一導航項→k 的大圓距離;
實飛腿 = `wp_seq == k` 期間逐點累加的地面距離):

| 量 | Pioneer PNP | HERO PNP |
|---|---|---|
| 固定翼段 規劃 | 35,168 m | 34,051 m |
| 固定翼段 實飛 | 34,728 m | 33,543 m |
| **比值** | **0.987** | **0.985** |
| 全程比值 | 0.991 | 0.988 |

比 1 **小**:L1 切內角,飛出來比折線短。誤差不是平均分布的 ——
長邊(3,022 m)比值 0.99–1.01,**掉頭短邊(271–567 m)比值 0.85–0.93**,
全部的偏差都集中在掉頭段。

> ⚠️ **訂正**:先前報過「實飛是規劃的 1.66 倍」。那是分母用錯造成的,
> 拿實飛固定翼段去比一個對不上任何定義的數。同一份舊資料重算也是 0.987。
> 「規劃全程」至少有三個互不相同的定義,講數字必須指明是哪一個:
> `BuiltPath.total_length_m` 34,486 / 導航項 2D 折線 35,466 /
> **全部**任務項折線 26,275,279(`DO_CHANGE_SPEED` 的 lat=lon=**0**,Null Island)。

### 1.2 轉彎:飛控轉得比規劃器認為可能的還緊,而且是系統性的

| 量 | Pioneer PNP | HERO PNP |
|---|---|---|
| `ROLL_LIMIT_DEG` | 20° | 25° |
| 實測峰值坡度 | 23.3° | 29.2° |
| 超出上限 | +3.3° | +4.2° |
| R_設計(規劃器實際使用) | 160 m | 100 m |
| R_理論 = V²/(g·tanφ) | 129.5 m | 78.9 m |
| **R_實得(實飛量到)** | **112 m** | **68 m** |
| **實得 / 理論** | **0.865** | **0.861** |

兩台的比值只差 0.5%。**這是滾轉迴路的系統性過衝,不是某一台的巧合** ——
而單飛一台在原理上分不出這兩者,這就是跑兩種機型換來的東西。

由峰值坡度反推的半徑(Pioneer 109.4 m、HERO 65.9 m)與實測(112 / 68 m)
只差 2.3% / 3.1%,機制對得上:**坡度過衝 → 半徑變小**。

### 1.3 我落地前寫死的預測錯了 —— 錯在哪裡值得記

預測:航道間距 270 m ⇒ 掉頭需 R = 135 m ⇒ HERO 只需坡度 15.3°,
距 25° 上限還有 9.7° ⇒ **不會**飽和。

實測:HERO 掉頭段 p95 = **25.0°**,照樣飽和。

錯因:我把掉頭建模成**一段 180° 弧**。匯出的航線其實是
**兩個 90° 轉角**夾一條 271 m 的短邊,而 L1 在航點上的銳角一律用滿坡度,
與該機還剩多少半徑餘裕**無關**。

⇒ **設計結論**:「半徑餘裕夠不夠」預測不了「坡度會不會飽和」。
餘裕真正決定的是**航點追蹤品質**:

| | Pioneer | HERO |
|---|---|---|
| 航點通過誤差 中位 | 13.8 m | 36.1 m |
| 航點通過誤差 最大 | **71.3 m** | **37.4 m** |
| 超出 `WP_RADIUS`=60 | 5/35 | **0/35** |

(Pioneer 的中位較小但**最大值較大**:它在多數航點上準,在掉頭航點上失準。
數值密集在 60.0–60.8 = `WP_RADIUS` 本身,那是**接受半徑**不是誤差。)

### 1.4 空速追蹤沒有問題

兩台的實得空速中位都**恰好等於**指令值(21.50 / 19.00),p05–p95 帶寬 ±0.1 m/s。
速度通道不是瓶頸,**前提是 `AIRSPEED_MIN` 有低於該機巡航** —— 見 §2.1。

### 2.2 ❌ 未接:規劃器對整支機隊只用**一個**轉彎半徑

`mission/swarm_coordinator.py` 裡有**兩處**,而且**不一致**:

- v2 直通管線:`_R = max((u.turn_radius for u in uav_states if u.turn_radius > 0), default=50.0)`
- 舊管線:`fw_uav = next(u for u in uav_states if u.turn_radius > 0)` —— 取**第一台**

實測混編 `[Pioneer(160), HERO(100)]`:

```
送進去的半徑: Pioneer 160.0, HERO 100.0
IDP_Solver 收到的 min_turn_radius : [160.0]
PathAssembler 收到的 turn_radius  : [160.0]
```

HERO 能用 100 m 轉彎,實際被用 160 m 規劃 ⇒ 它的機動優勢在規劃階段就被丟掉。
這是異質機隊最核心的一個洞。

### 2.3 ❌ 未接:`FixedWingConstraints` 內的空速是**虛構**的

規劃器拿 R 反解一個空速,φ 寫死 **45°**、safety 寫死 **1.2**:

```python
_v_needed = math.sqrt(default_turn_radius * 9.81 * math.tan(math.radians(45.0)) / 1.2)
```

Pioneer(R=160)反解出 **36.2 m/s**,不是它的 21.5;φ=45° 也不是它的 20°。
因為只會 round-trip 回原本的 R,幾何目前沒錯 ——
但那個物件的 `cruise_airspeed_mps` 欄位是假的,任何下游改讀它就會拿到垃圾。

### 2.4 ❌ 未接:`core/base/airframe.py` 的其餘欄位仍零消費者

爬升/下降航跡角、質量、續航、`min_mission_airspeed_mps`、
三個 VTOL 高度 —— 目前只有 `vtol_profile.py` 在 `TYPE_CHECKING` 下匯入型別。

### 2.5 ❌ 未接:UI 輸入通道

`ui/widgets/vtol_recon_panel.py` 的空速輸入是 `setRange(20.0, 34.0)`,
HERO 的 19.0 **打不進去**。而且面板只有一組欄位,沒有「哪一台」的概念。

## 三、設計

### 3.1 原則:機體是資料,不是分支

`Airframe` 已經是 frozen dataclass。異質化**不要**用 `if vehicle_type == ...` 展開,
而是讓每一層收一個 `Airframe`(或每台一個),把「這台的能力」當參數傳下去。

理由:`turn_radius > 0` 這個判別式已經把三件事混在一起
(能不能懸停 / 起降要不要跑道 / 巡航受不受最小半徑限制),
`Airframe` 把它們拆成 `can_hover` / `needs_runway` / `has_turn_radius` 三個布林。
再加一層分支只會把混淆搬到別處。

### 3.2 規劃層:半徑從「機隊一個」變成「每台一個」

現行資料流:

```
drones[] ──► uav_states[] ──► _R = max(所有 turn_radius) ──► IDP_Solver
                                                        └─► PathAssembler
```

目標:

```
drones[] ──► uav_states[](各自帶 airframe)
                    │
                    ├─► 分配階段:用**各自**的 R 與 V 估成本
                    └─► 路徑生成:每台用**自己**的 DubinsTrajectoryGenerator
```

⚠️ 這裡有個順序陷阱:分配(誰去哪一區)與半徑互相影響 ——
半徑影響路徑長度,路徑長度影響分配,分配又決定哪台用哪個半徑。
現行 `max()` 之所以「能動」,正是因為它把這個耦合切斷了。
**先做路徑生成的逐機化(分配結果固定),量出差多少,再決定要不要動分配。**

### 3.3 可行性判準:用理論半徑,不要用設計半徑

實測:用**設計半徑**當判準,Pioneer 有 **3/9** 個轉角被判成不可行,
而那些轉角飛機實際飛得過去(只切內角 19.6–20.5 m)。用**理論半徑**則 9/9 通過。

| 半徑 | 用途 |
|---|---|
| R_理論 = V²/(g·tanφ_max) | **可行性判準**(過不了就是真的過不了) |
| R_設計(留裕度) | **航線生成目標**(希望飛成什麼樣) |
| R_實得 ≈ 0.86 × R_理論 | **實際會發生的事**(不要拿來規劃,但報表要標) |

把三者混用是目前最容易出錯的地方。

### 3.4 轉彎交給誰:結論是**兩邊都要,但職責不同**

- **規劃階段**保留轉彎半徑,做**可行性檢查**(用 R_理論),
  在上傳之前就攔掉幾何上不可能的轉角。
- **飛控**負責實際轉彎,而且它會用滿坡度、超出上限 3–4°、
  轉出比理論值小 14% 的半徑。規劃階段**不要**試圖預測這個,
  只要確保「即使飛控保守到只用理論半徑,轉角也容得下」。

⇒ 判準寫成:`R_理論 · tan(偏轉角/2) ≤ min(前腿, 後腿)/2`(已實作於
`FixedWingConstraints.is_path_executable()`,`tests/test_turn_feasibility.py` 19 條鎖)。

### 3.5 覆蓋品質:切內角會讓航道末端漏掉

掉頭段比值 0.85–0.93,對應航點通過誤差最大 71.3 m(Pioneer)/ 37.4 m(HERO)。
**這不是航跡長度問題,是覆蓋品質問題** —— 每條航道的末端有數十公尺沒被掃到。

未驗證的兩個候選解:(a) 航道兩端各外推一段延伸腿;(b) 縮小 `WP_RADIUS`。
兩者都會加長航程,要量過再選。

## 七、B 階段(已完成 2026-09-05)

### 7.1 ⚠️ 動手前先訂正一個會誤導設計的量

`BuiltPath.total_length_m` **不是**飛出來那條路徑的長度。ENTRY / TRANSFER 都走
`_dubins_waypoints(simplify=True)`,只保留端點、把弧丟掉;而 `total_length_m` 計的是
**Dubins 弧長**。兩者在實測中差 −2,426 到 +1,004 m。

直接後果:**單獨換 `DCCPPPathBuilder` 的半徑,一個航點都不會動**。
實測 R=40 / 100 / 160 三種半徑產出的航點列**逐位元相同**(md5 一樣),
只有 `entry_length_m` / `transfer_length_m` 變。

⇒ 「只改 builder、不動 IDP」這個看似最小侵入的做法,**在飛出來的航線上完全是惰性的**,
   卻會讓 `total_length_m` 這個回報值變小,看起來像有效。
   這正是本專案反覆踩的那類失效,差一點就照做了。

真正會動到航線的是 **IDP 排出的條帶順序與方向**。

### 7.2 範圍的正確切法

| 階段 | 屬於 | B 階段動它嗎 |
|---|---|---|
| `_partition_joint` / `_partition_balanced`(誰拿哪些條帶) | **分配** | ❌ 維持機隊半徑 |
| `_solve_single`(該機條帶的**順序與方向**) | **路徑生成** | ✅ 改逐機 |
| `DCCPPPathBuilder.build`(幾何與長度) | **路徑生成** | ✅ 改逐機 |

`_solve_single` 有三個呼叫點:兩個在 `_partition_*` 裡(分配)、一個在 `solve()` 第 2 步
(生成)。只改第三個。

### 7.3 實作

- `_solve_single` 的 `cost` 是**必填位置參數**,故意不給預設值 —— 漏傳一個呼叫點會直接
  `TypeError`,而不是靜默退回機隊快取。
- 逐機成本快取用**不同的 instance**。`_DubinsCostCache.cost` 的 memo key 只有幾何
  (x, y, heading)**沒有半徑**,共用一份 `_cache` 會把 A 機的成本靜默餵給 B 機。
- **收據**:`UAVPlan.turn_radius_m` 與 `BuiltPath.turn_radius_m` 都從**產生公尺的那個
  物件**讀回(`cost.R` / `gen._radius`),不是輸入的副本 —— 否則「有傳進來」與
  「有用到」分不開。結果多一個鍵 `turn_radius_by_uav`。
- **不變式**:排序半徑必須等於生成半徑。不一致丟 `TurnRadiusMismatch`,而且該例外
  **必須穿過** v2 外層那個 `except Exception`(第一版沒做,守衛照樣觸發卻被吞掉,
  退化成舊 solver 只留一行 WARNING,測試看到的是「沒有拋錯」)。
- 舊管線的 `next(...)`(取清單第一台)改成 `max(...)`,消掉順序相依。
- 多旋翼(`turn_radius == 0`)**維持**既有行為拿機隊半徑。改成直線會動到既有 golden,
  屬於另一個獨立的行為變更,不混進來。

### 7.4 實測結果

| 量 | 改前 | 改後 |
|---|---|---|
| 單飛 HERO 的航點折線 | 35,466.2 m | **34,373.2 m**(−1,093 m,−3.08%) |

### 7.5 驗收怎麼做的

30 條值層級鎖 + **22/22 突變全咬**,外加一輪 20 個 agent 的對抗式審查。四件值得記的事:

1. **一條測試原本是恆綠的** —— 它去 `result["results"]` 找 `per_uav`,但那裡裝的是
   `MDTSPResult`(沒有這個屬性),迴圈一次都沒跑。是我自己檢查「它到底量到什麼」才發現。
2. **突變實驗抓到我實作裡的真 bug** —— 一致性守衛被外層 `except Exception` 吞掉。
   測試先紅,才有那個 `except TurnRadiusMismatch: raise`。
3. **前兩個分配守衛都沒有鑑別力** —— 這組幾何下 joint 搜尋不論用哪個半徑都收斂到同一組
   切分,所以「條帶數」與「條帶歸屬」都測不出分配被改掉。真正分得出來的是**呼叫結構**:
   正常 `{160: 45 次, 100: 1 次}`,分配被改成逐機之後變 `{100: 46 次}`。
4. **對抗式審查在我自己寫的鎖裡又找到四個洞**(見 §7.7),其中兩個是真的實作缺陷。

### 7.6 B 階段**沒有**解決的

- 分配階段仍用機隊半徑(範圍外,刻意)。
- 多旋翼仍拿固定翼半徑(§2.2 量到多飛 3,937 m / +13.1%)。
- **產品端仍然只有一個半徑**:`ui/main_window.py` 在 `for i in range(num_drones)`
  迴圈裡把同一個面板純量寫進每一台的 dict。所以今天實務上機隊裡從來不會出現兩個半徑,
  `max()` 是對一組相同值取最大。B 階段修好了規劃層,**要看到效果得先做 D 階段(UI)**。
- IDP 的時間目標退化:生產端的 `uav_inputs` 不含 `speed`,
  `max(float(uav.get('speed', 0.0)) or 0.0, 1e-6)` 讓每台都是 `1e-6`,
  min-max **時間**變成 min-max **距離**。一行可修,但會動到分配,留給後續階段。
- `total_length_m` 與航點折線不一致(§7.1)。這個量會餵給 makespan 與續航判斷。


### 7.7 對抗式審查找到、且已修的四項

20 個 agent(4 個攻擊面 × 逐項驗證),確認 14 項。扣掉已知範圍外的
(UI 只有一個半徑、`speed` 沒傳),真正屬於這次改動的有四項:

| # | 問題 | 為什麼會漏 |
|---|---|---|
| 1 | **同名測試** `test_solve_single_refuses_to_default_its_cost` 定義了**兩次** | Python 後定義覆蓋前定義,pytest 收 22 個而檔案裡有 23 個 `def test_*`,**零警告**。而且被覆蓋的那一份用空的 scan lines,函式在碰到 `cost` 之前就回傳,`pytest.raises(TypeError)` 是被別的原因滿足的 —— 就算它有跑也是恆綠。已刪,並加一條 AST 守衛。 |
| 2 | **solver 側的小半徑沒有具名錯誤** | 我在 builder 補了 `_dubins_for` 的具名重拋,**但 `IDP_Solver.cost_cache_for` 漏了**。`R=3` 反解出空速 4.95 < 失速 7.0,`FixedWingConstraints` 丟的訊息是「失速速度必須 < 巡航空速」—— 完全沒提半徑,又被外層 `except Exception` 吞掉,靜默退回舊 solver。已加 `TurnRadiusUnusable` 並讓它穿過那個 except。 |
| 3 | **沒分到條帶的 UAV,收據回報 0.0** | `UAVPlan.turn_radius_m` 留在預設 0.0,而 builder 仍寫入真實半徑 ⇒ 收據變成 `(0.0, 160.0)` 這種自相矛盾的一組,讓一致性不變式在**合法**計畫上假紅。只要機隊台數多於條帶數就會發生,而面板允許 2–12 台。 |
| 4 | **`-inf` 靜默退回機隊值** | `if radius is None or float(radius) <= 0.0: return self._cost` 排在有限性檢查**前面**,`-inf <= 0` 為真。NaN 更糟:`NaN <= 0` 為假、`abs(NaN - x) > tol` 也為假 ⇒ 所有讀回檢查都放行。順序已對調。 |

另外訂正了三條**名不副實**的測試(名字承諾的比身體檢查的多):
一條宣稱能擋「每次都重建生成器」(用 `set()` 丟掉次數,擋不到)、
一條宣稱能證明「收據不是輸入的副本」(那個情境下兩者本來就相等)、
一條叫 `..._is_bit_identical_to_before` 卻一個航點都沒看(已補一條真的比航點的)。

### 7.8 審查確認、但**刻意不在這階段修**的

- **UI 只有一個半徑**(高嚴重度):審查用真實生產呼叫路徑驗證,對每一個
  介面做得出來的組態,規劃出的任務**與改動前逐位元相同**。B 階段交付的能力
  在產品上**沒有路徑到達**。這是 D 階段。
- **`speed` 沒進 `uav_inputs`**:min-max 時間目標退化成距離目標。一行可修,
  但會動到分配。速度比超過約 1.7:1 時會造成 1.3–2.2 倍的 makespan 退化;
  現有兩台是 21.5 / 19.0(比值 1.13),所以今天分配結果不變。
