# §五 RRD 的主結論:一個 bug 造出兩個母體

### 機制(這是「指令從未送達」,不是飛行問題)

`runin → wait` 切換時,那一發 `_goto` 的 lat/lon/alt **逐位元相同**
(`ring_point_of(i)` 不變;`hold_alt=0` ⇒ `hold_alt_of()` 就是 `perch_of()`),
**只有 radius 由 30 變 1300**。

而 `_goto` 的變更偵測器存的是 `wp_pt = (lat, lon, alt)` —— **radius 不在裡面**:

```python
prev = self.wp_pt.get(i)
moved = (prev is None or abs(prev[2] - alt) > 5.0
         or dist_m(prev[:2], (lat, lon)) > move_tol)
```

⇒ `moved = False` ⇒ 那發 `DO_REPOSITION` **根本沒送出去**,飛機掛著舊的
`param3=30` 繼續直飛。`hold_radius` 只有在下一個 **30 s keepalive** 補發時才生效。

⇒ **一架會不會起彎,取決於它進 wait 時距 30 s 格點還有多久 —— 逐趟隨機。**

驗證:用 keepalive 相位預測「會不會起彎」命中 **15/16**;
五架起彎者的「預測補發 → 實測起彎」殘差 +2.0 / +0.4 / +0.9 / +2.2 / +0.8 s
(= 滾轉建立時間),**無一早於預測**。

見 §六。Δ放行 1.1–37.0 s 全部直接傳到觸地。
兩個已知死路見 §七.5。**這是 S2 之後的主線。**

⚠️ n=8 判準:同步要靠**時間錯開**不能靠**空間會合**。
逐機時序 σ 必須 ≤ 3/d2(8) = **1.05 s**(d2(8)=2.847)。

### 8.2 ⚠️⚠️ 埠帶在 N≥11 互撞 —— **n=8 之前的硬阻擋**

`swarm_sitl_up.sh` 五條埠帶,stride 都是 10:

    SITL     5760 + 10i        MAVROS   5860 + 10i
    AeroPlan 6760 + 10i        tot_node 6860 + 10i
    編隊層    6960 + 10i

⇒ `i = 10` 時 SITL 撞上 MAVROS ⇒ **N ≥ 11 開始互撞**。
⇒ **N = 16 有 18 對衝突**(SITL∩MAVROS 6、AeroPlan∩tot_node 6、tot_node∩編隊 6)。

⇒ 8 架 × 2 群 = 16 台**跑不起來**。修法是換 stride 或改成不重疊的帶 ——
**只動一個檔**,但必須在開 n=8 之前做完。

### 8.3 `tot_node.py` 的 `_tick` 太大

4539 行的檔案,`_tick` 把狀態機 + 導引 + 遙測混在一起。狀態機該抽出來。
**這不是 bug,是讓下一個 bug 更難藏。** 優先序低於 8.1 / 8.2。

### 8.4 已知會壞但還沒發作

* `miss_far_m` 自動夾寬到 **69.7 km**(公式用「當下最遠距離」)⇒ **miss 出口實質失效**。
  要進生產路徑必須改成用環半徑。
* 守環的**圓心畫在環上**(§七.3)。`release_at_ring` 打開後 `hold_ring` 整段消失,
  所以這是**可移除的設計**,不是要修的 bug。
  `hold_radius=1300` 仍保留給 ALIGN 的 `hold_ring` 與 missed 的守點盤旋(那兩處真的要繞)。

# §十三 使用者定調(不要重新討論)

* **可靠度 > 散布 > 終端速度**(2026-08-18)。逐機真觸地率先做到 ≥90% 再談散布。
* **3 秒是單群 8 架打完**,不是 16 台;兩群可以錯開 ⇒ 逐機時序 σ ≤ 1.05 s。
* **最終規模 8 架 × 2 群 = 16 台。**「n=2 才成立」的解不算解。
* **同步靠時間錯開,不靠空間會合。**
* **SITL 量測、Gazebo 表演。**
* **靜默失敗與吃到舊參數不可再發生**(優先於新功能與調參)。
* **精度沒有授權可以拿去換** —— 只授權了「降速度保散布」。

# §十四 ⭐ 建議升格成常設規則:req / cmd 雙欄

到今天為止,反覆出現的失效類別是同一個:
**「開關開著,但那段邏輯 / 那道指令從來沒有真的發生」**,四次:

    predict_hz 沒接線 · ITCG 從未武裝 · ring_pace 守衛恆偽 · 半徑指令被去重器吃掉

根因不是四次獨立的粗心,是**沒有任何地方記錄「這一拍,每個致動器實際要求了什麼」**
⇒「有下令」和「有生效」永遠分不開,而每次都要燒掉一整批才發現。

S2 的 `req_radius_m` / `cmd_radius_m` 是這個想法的縮小版。建議推廣:
**半徑、速度、姿態,每一個致動路徑都記這兩個量。**

⚠️ 推廣時必須帶上這條,否則會複製出一批假綠燈:

> **判定量是 `req_*`(每拍都寫),不是 `cmd_*`。**
> `cmd_*` 是 hold-last-value,在開關關閉時可能與開啟時完全相同。
> 兩者背離的長度 = 指令被吃掉的時間。

這比重寫便宜兩個數量級,而且直接殺掉那個失效類別。
