# 實作 2026-10-17：匯入 .waypoints（多檔 → 每架一份）與飛完下載每台 .bin

使用者 2026-10-17 定調兩個功能：**(1) 可以匯入 .waypoints**（Mission Planner 的 QGC WPL 110；順便收 QGC .plan）、

## 0. 一句話

實跑才學到的三件事（都寫進腳本註解與記憶）：
1. `plane.parm` 的 `ARMING_REQUIRE 0` ⇒ 開機就是 armed ⇒ 飛控回 "Disarm for log download"（第一次跑 G1 就 FAIL）。
2. **飛控一開始傳日誌就把正在寫的那份關掉、另開新檔**（LASTLOG 每次 list／下載／取消都 +1），關掉前再寫一個 flush
   區塊 ⇒ 磁碟檔比列表 size 多 8,192 B；下載到的是列表當下的前 size 位元組。實飛 `LOG_DISARMED=0` 上鎖後日誌已關閉，
   size 就是最終大小，沒有這個差。
3. `LOG_ENTRY.id` 對應檔名 = 最舊檔號 + id − 1，不是 LASTLOG。

## 5. 已知限制

- 匯入只做「每檔一架」；一個檔要分給多架、或把多檔接成一架的任務不在範圍。
- 匯入預覽不重建圍籬（刻意，觀測無副作用）；要圍籬請走規劃器。
- 日誌下載同一條鏈路同時一個；「全部下載」是每條鏈路各一個（飛控本身也只服務一條鏈路）。
- 實機數傳慢（57600 ≈ 8 KiB/s）；USB／SITL 快。未在真板子上驗（沒有實機）。
- `LOG_ENTRY.id` 是「從最舊一份起算的序號」，開機 `Prep_MinSpace` 刪舊檔會整體前移 ⇒ 檔名用 time_utc，不用 id 對應舊檔。
- 「挑最新一份」是以 id 最大者為準：`LOG_DISARMED=1` 的機器每次傳輸都會讓飛控另開一份小日誌，第二次按「下載」會
  拿到那份小的（HUD 訊息有列大小，看得出來）；實飛預設 `LOG_DISARMED=0`，落地上鎖後最新一份就是這趟的日誌。
- 列表逾時會先自動補要一次再報失敗（最壞 16 s）；鏈路的失敗同時也發 `status_text`，HUD 狀態列會看到兩則。
- 圖層鍵（`mission_view.fc_layer_key`）：讀回 `uav<n>`、匯入預覽 `uav<n>-import`、單檔載入 `loaded`；舊呼叫（sysid 與 kind
  都 None）才是「先清全部層」。「清除全部」會同步丟掉匯入指派（`_loaded_mission` 照舊不動）。
- 規劃前的 2D 清場（`clear_all_display_layers_js`）會跳過任務層（`options.fcMission`），匯入／讀回預覽在規劃後仍在。
