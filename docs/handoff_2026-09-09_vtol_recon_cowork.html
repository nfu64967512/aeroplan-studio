演算法 · 論文沒有而本研究補上的兩件事

四個步驟：決定掃描方向 → 切掃描帶（實作 Wang et al. 2025, Defence Technology 47:197–215 的 Eq.7）→ 分配給各機（min-max makespan）→ Dubins 串接起飛／掃描／轉場三段。

相機模組　core/recon/sensor_footprint.py

讓「影像要看多細」與「飛多高、一趟掃多寬」可以互相換算。公開 API：compute_footprint、swath_width_m、gsd_m_per_px、altitude_for_gsd_m、effective_sweep_width_m。掛載角上限硬編在 _MAX_LOOK_ANGLE_DEG = 85.0。

HARVEST 側是另一套相機模型（hv_dccpp/platform.py，用焦距與像素間距，不是 FOV）。兩套並存，改一邊不會影響另一邊。

獨立覆蓋率驗算　core/recon/coverage_verifier.py

規劃完之後把作業段航點網格化重算一次覆蓋率與漏掃格，不讓規劃程式自己說自己對。

已知結構性缺口（未修）。驗算只吃 (lat, lon)，從不讀航點的 alt，再配一個由面板航高算出的單一 sweep_width_m。所以當各機實際高度不同時，它回報的覆蓋率是對「假設全隊都飛設定高度」成立，不是對實際任務成立。這正是高度被抬高卻躲過驗算的原因 —— 修高度問題時要順手補這個。

四個靜默缺陷

四個都屬於同一類：不會報錯、log 看起來正常、但結果是錯的。

缺陷① 掃描帶重疊率失效

中線 =（dw_top + dw_bot）/ 2 時 w_ovl 項剛好對消：

dw_mid(l) = ½[(l−1)(w_i−w_ovl) + l·w_i + (l−1)·w_ovl] = ½·w_i·(2l−1)

⇒ 中線間距恆等於 w_i，與重疊率無關。

訂正報告的措辭。報告寫「怎麼調結果都一樣」，只對了一半。中線間距確實不變，但條帶數量會隨重疊率遞減（:351 的 step 是 +），所以調高重疊率會讓覆蓋率變差，方向是反的。

實測條件 2.0×1.5 km、w_i = 110.88。只修中線公式而不修 :351 的 step，n_layers 仍然是錯的。這個錯誤措辭同時存在於報告與 test_dccpp_strip_pitch.py:14 的 docstring，修的時候一起更正。

論文印的是 +；無法斷定是原文誤植或 PDF 抽取損壞，以物理自洽為準。

缺陷② 規劃器不認得 VTOL　已在樹上

真正的判別式是 if u.turn_radius > 0，不是 vehicle_type；而 vehicle_type='vtol' 被降級成 VehicleType.MULTIROTOR（那個 enum 根本沒有 VTOL 成員）。QuadPlane 的 turn_radius 合法地大於 0 ⇒ 被當固定翼。plan_coverage_dccpp() 當時連 transition_alt 這個參數都沒有，起降參數是 runway_length_m 那一組，而 VTOL 偵察頁沒有跑道欄位 ⇒ 吃預設值。

Home（地面） ──純垂直──> 轉換高度 ──前向過渡──> 固定翼爬升 ──> 巡航高度
垂直段會弄壞三個下游（都已修，接手時不要退回去）：

① SITL 生成朝向只比對 waypoints[1]，同經緯度算不出方位 ⇒ 靜靜退回 0°。② NFZ 避障後用水平弧長比例重採樣高度 ⇒ 垂直段佔比 0，整段爬升被擠掉。③ 避撞的高度偏移窗是純索引式，沒有起降段守衛 ⇒ 會把地面點抬高 ⇒「在半空中降落」。

仍未修：BuiltPath.total_length_m = entry + operation + transfer，沒有 takeoff / landing ⇒ total_makespan 系統性低估。修它會同時踩紅 test_dccpp_pipeline.py 的兩條特徵化測試。

MAVLink common.xml 的 enum SPEED_TYPE：0 = Airspeed、1 = Groundspeed。匯出檔設的是地速下限，根本沒設巡航空速；上傳側型別對但值是 3.0，遠低於 QuadPlane 的 AIRSPEED_MIN ⇒ 會被夾掉。兩條路都沒有真的設到巡航空速。

缺陷④ QuadPlane 在 SITL 飛不起來

根因是 sitl/default_params/plane.parm:84 的 ARMING_REQUIRE 0，讓四軸馬達一直停在最低油門。

判別法：PWM 0 = 該通道沒指派馬達功能；PWM 1000 = 有指派但被命令關掉。兩者意義完全不同。另一個錯誤直覺：--model quadplane 只決定物理模型，QuadPlane 功能要靠參數開 —— --model quadplane ≠ Q_ENABLE=1。

修法：注入，不是檢查。對 vehicle == 'VTOL' 產生 vtol_enforced.parm 並掛進 --defaults 鏈：

Q_ENABLE 1 / Q_FRAME_CLASS 1 / Q_FRAME_TYPE 1
SERVO5~8_FUNCTION 33~36
ARMING_REQUIRE 1        ← 覆蓋 plane.parm 的 0

關鍵是注入不是檢查：檢查只會事後告訴你壞了；注入直接讓它是對的，而且不依賴任何人維護 plane.parm。

排序有實質意義。--defaults 後面覆蓋前面。目前唯一真的在注入的地方是 scripts/hv_sitl_flight.py:176-189，六份的順序是 plane.parm → vtol_default.parm → identity.parm → vtol_enforced.parm → <UAV>.param → firmware_override.parm —— 強制檔排第 4，<UAV>.param 排在它後面。今天安全（那些 .param 只有 Q_ENABLE,1），但只要哪天含 ARMING_REQUIRE 就會被蓋掉。hv_sitl_flight.py:19 的 docstring 只列五份，已過時，不要照抄。
產品啟動器沒有這個。mission/sitl_launcher.py 完全沒有 VTOL_ENFORCED_PARAMS，:571 寫的 SCHED_LOOP_RATE=50（測試期待 200）。hv_sitl_flight.py:14 自己就逐字寫著「那一版 launcher 不會掛上去」。

⇒ 走 GUI 產品路徑起 SITL，現在仍然會踩到這個 bug。

順帶三個 PreArm 修正

  1. VTOL land too short —— 飛控用它自己的 AIRSPEED_CRUISE 算煞停距離，跟面板速度無關。修法是把 land_approach_m 取 max(back_transition, 飛控煞停距離 × 1.25)。
  2. Gyro rate —— SITL 模擬陀螺儀 400 Hz，300 × 1.8 = 540 > 400 恆擋 ⇒ loop rate 300 → 200。現行 launcher 是 50
  3. 真解鎖優先 已在樹上 —— sitl_link.py:865 _arm_with_prearm 先發正常 ARM 吃真 PreArm，被擋才 force(21196) 並大聲警告。但產品呼叫點目前全部傳 force_fallback=True，所以「0 次強制解鎖」是那一趟的觀測結果，不是結構保證。

驗證方法論 · 本研究最可複製的部分

四條紀律，寫在 docs/design_2026-09-05_heterogeneous_vtol_planning.md §四：

  1. 值層級鎖，不是源碼層級鎖。量「實際產生的中線間距是多少」，不是 grep「那一行有沒有寫 w_ovl」。源碼鎖驗的是那一行長什麼樣，改上游、下游、旁路全部免疫，補鎖是軍備競賽。
  2. 可觸發性前置斷言。每條測試先斷言「這個設定真的能讓 X 發生」，再斷言 X 的值。否則「量到 0 次」與「量測器根本不可能觸發」長得一模一樣。
  3. 突變驗證。故意把程式改壞，確認測試真的會轉紅。臂數不夠不算數，要涵蓋靜默失效臂。
  4. 逐檔 --collect-only。防「收集 0 項卻不報錯」的假測試。

突變測試怎麼跑

scratchpad/bite_*.py 共 16 個檔，其中 bite_lock.py 是檔案鎖本身，實際突變臂腳本 15 支，合計約 224 臂。

ARMS = [(名稱, 檔案路徑, old 片段, new 片段), ...]
拿 BiteLock → 逐臂就地改寫源碼 → subprocess 跑 pytest → finally 還原
→ anchor 命中次數 != 1 就 SKIP → rc 非 0 記 BITES，否則 SURVIVED
三個必須知道的陷阱。

①　突變腳本會就地改寫生產源碼。同時跑兩份會把突變留在樹上，其中有些不會報錯只會靜靜飛錯。bite_lock.py 是為此加的互斥鎖 —— 一定要透過它跑。

②　對照組不綠就不要跑突變。對照組本來就紅的話，每一臂都會「看起來被咬到」，全部是假陽性。今天 bite_alt_cap.py 的對照組是 20 紅 ⇒ 它的 17 個可套臂會產生 17 個假陽性，現在不要跑它。

③　anchor 會失效。bite_alt_cap.py 的 23 臂裡有 6 臂的 anchor 在現行 collision_avoidance.py 命中 0 次 ⇒ 會 SKIP。今天唯一安全可重跑的是 bite_fov_cone.py（17/17 臂齊全，對照組 117 passed / 0 failed）。

已知的假測試：tests/test_heterogeneous_nfz_planner.py 被 git 追蹤、檔名符合 test_*.py、pytest 收集 0 項且不報任何錯（rc=5）。整檔 0 個 def test_，實際是 if __name__ == '__main__' 的腳本。

設計上是三級，以 assignment= 切換，逐級以前一級為起點 ⇒ 保證 joint ≤ contiguous ≤ index：index（最舊的等索引切塊）、contiguous（連續切塊 + 邊界爬山 + 區塊↔UAV 窮舉）、joint（論文 §3.3 聯合 MDTSP，放棄連續限制，局部搜尋逼近 minmax）。

core/dccpp/idp_solver.py.bak 是 4 月的舊 numpy 版，沒有 joint，不是復原來源。

做完 WP-C 一定要接著做 WP-D。joint 會產生交錯指派（例如 UAV3 拿 [6,8,10]、UAV4 拿 [7,9,11]），兩架因此同時飛在相鄰條帶上，間距會掉到 1.6 m。單獨上 joint 而不修避撞，是把安全問題引進來。

牆鐘預算要用確定性預算（評估次數），不要用秒數 —— test_solver_wallclock_independence.py 鎖的就是這件事。

  1. 迭代到收斂（加 max_rounds）。單輪解不完。
  2. 高度累加上限（加 max_alt_offset_m / _effective_cap）。沒有上限時每輪再抬一次，120 + 10×30 = 360 m 就是這樣來的。
  3. 停滯保險絲要真的能燒斷。原本 _resolve_altitude 先無條件 actions.append(...)，之後才在套用迴圈裡對起降段 continue 跳過 —— 而 t=0 的衝突正好就在那些地面點上 ⇒ new_actions 永遠非空 ⇒ 停滯判斷永遠不會觸發。修法：在迴圈一開頭就跳過「衝突點本身在起降段」的衝突。只在事後過濾「動作有沒有動到航點」不夠 —— 判準必須是衝突點本身動不動得了。
  4. 撞到上限要大聲。靜靜停下來和靜靜飛到 360 m 一樣糟。

另外三個獨立的坑

生成點間距不能等於門檻。生成點用 111320.0 m/deg 排，而 _haversine 用 EARTH_RADIUS_M = 6378137 ⇒ 2πR/360 = 111319.4908 m/deg。50.0 m 名目間距被量成 49.999771 m，比門檻低 0.23 mm ⇒ if dist < min_sep 在 t=0 對每一組相鄰機必定成立，而且 cos(緯度) 在兩邊約掉 ⇒ 與緯度無關、必然發生。衝突本身是假的。修法：間距改 max(50, min_sep × 1.2)，且排點與量距改用同一個地球半徑常數 —— 兩件都要做，只換常數仍會壓在刀鋒上。

alt_offset_m < min_separation_m 是無解組態。面板的 get_params() 沒有 alt_offset_m 這個鍵 ⇒ 永遠退回預設 30，而 min_separation_m 送的是 50。30 < 50 ⇒ 純高度錯開在數學上解不開。

temporal 策略原本是完全 no-op：它插入的 loiter 航點與參考航點同經緯度同高度，而時間由「累積距離 / 速度」推出 ⇒ 零長度線段貢獻 0 秒延遲；AvoidanceAction.delay_s 沒有任何下游會消費。已改為大聲報錯並退回 altitude。

避撞目前只在 GUI 路徑跑，headless／匯出路徑沒有保護。這是待解項。
