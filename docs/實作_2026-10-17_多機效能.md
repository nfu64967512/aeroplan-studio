# 實作 2026-10-17：多機順跑——高頻串流、遙測合幀、地圖批次更新、3D 取樣插值

使用者：「是否可以再讓效能更好，讓我在多機可以順跑？」接著定調：「最主要的是畫面看到要流暢，包含 SITL 的 Hz 數要高，
飛行時 3D 建模也要順暢，不能轉向了頭還沒跟上」。本機 `vtol` 分支，未 commit。

## 0. 一句話

以前：ArduPilot 串流只要 4 Hz（機頭還用 VFR_HUD 的整數 heading ⇒ 一格一格跳、轉彎慢半拍）；每條鏈路每秒仍 emit 二十幾幀，
6 架就是主執行緒每秒 150 幀，每幀各自重繪一張卡片、送兩段 ~2 KB 的 2D JS（連 SVG 圖示一起送、每幀重建 Leaflet 圖示）、
送一段 3D JS（每次 O(N²) 碰撞檢查）；3D 頁軌跡 1500 點每次渲染重新投影。現在：**串流拉到 20 Hz**（位置／姿態／VFR），
主視窗以固定 **30 Hz** 把每架最新一幀一次推到地圖（HUD 機卡另限 15 Hz），2D／3D 各一次批次 JS；機頭用 ATTITUDE yaw、
速度夠時依航跡方向轉；3D 改取樣插值（位置 Hermite、姿態四元數、短暫外推）讓 30 Hz 的資料在顯示幀率下連續；
渲染只在沒有飛機更新時才省電。

## 4. 驗收：平順度與機頭跟航線（真 Cesium 1.115、無頭 Chrome）

探針（scratchpad `probe_smooth.py`，結果 `runs/artifacts/PERF_2026-10-17/smooth_probe.json`）：飛機以 R=60 m、18 m/s 急轉（≈17°/s），
模擬鏈路收訊抖動（位置／姿態各 ±3 ms＋0–2 ms）、Python 合幀（33 ms＋1–5 ms）、IPC 0–4 ms，以 60 fps 逐幀讀實體位置與姿態。
舊版 = HEAD 的 main.html＋舊管線（4 Hz 串流、每則訊息各推一次、機頭用 VFR 整數 heading）；新版 = 工作樹＋新管線。

| 指標（4.5 s、269 幀） | 舊版 | 新版 |
|---|---|---|
| 機體沒動的幀 | **251** | 0 |
| 單幀最大位移 | 4.56 m | 0.33 m（18 m/s ÷ 60 fps = 0.30） |
| 顯示速度標準差 | 67 m/s（走走停停） | **0.63 m/s**（3.5%） |
| 倒退幀 | 0 | 0 |
| 機頭 vs 畫出的航跡（平均／最大） | 2.25° / 2.34° | **0.32° / 0.87°** |
| 顯示延遲 | — | 0.13 s（位置與機頭同一個延遲，所以永遠一致） |

斷訊 1.5 s 情境（新版）：期間 87 幀停在最後一筆（不外推、不漂），恢復時一幀跳回真實位置（約 21 m），0 倒退；延遲只升到 0.16 s。

## 5. 改後量測（3D 真渲染）

`tools/swarm_perf_profiler.py --mode both --steps 1,3,6 --dwell 6`，同一台機器（RTX 4070、ANGLE D3D11）、TCP 樁飛編隊軌跡（不需 SITL）。
「改前」= 本輪開工時的程式（每則遙測直推、Constant 屬性、60 fps 空轉）；baseline = 新頁面但每則遙測直推單架 API；
optimized = app 實際路徑（`TELEMETRY_FLUSH_HZ` 合幀＋`MainWindow._uav_batch_item` 組批次＋`update_uav_positions`）。CPU 為本行程樹跨核總和。

每架 10 Hz（與改前基準同條件）：

| N | FPS（改前 / 定稿） | CPU 改前 | CPU baseline | CPU **optimized（app）** | RSS 改前 → 定稿 |
|---|---|---|---|---|---|
| 1 | 21.8 / 21.7 | 68% | 48% | **41%** | 745 → 714 MB |
| 3 | 21.8 / 21.8 | 118% | 66% | **52%** | 892 → 718 MB |
| 6 | 21.7 / 21.9 | 150% | 99% | **59%** | **1201 → 725 MB** |

每架 20 Hz（定稿串流頻率）：optimized 51% / 58% / 82%（1 / 3 / 6 架），baseline 65% / 112% / 109%。

- 6 架時 CPU 約降到四成、記憶體不再每架 +75 MB。FPS 兩邊都停在 ~22：這台機器上 QtWebEngine 視窗的合成節奏，1 架也 22，與架數無關；
  插值讓機體在這個幀率下連續移動（§4），不再是 4 Hz 跳格。
  ⭐ 同日後續：這個 22 FPS **不是機器上限**，根因已找到並修好（Qt 視窗端 present 等 vsync ＋ CAD 模型上千個 draw call），
  10 架 VTOL 實測 21.3 → 60.2 FPS ⇒ 見 `docs/實作_2026-10-17_3D流暢度.md`。
- ⚠ 中途第一版 3D（樣本時間用 JS 收到時刻、Hermite 外推）曾量到 6 架 28%，但那版會走走停停／倒退（§6），已重做；上表是定稿。
- 無頭 `telemetry_bench --stages map3d`（逐架呼叫）：6 架 × 25 Hz 主執行緒 1.7%；批次呼叫下 runJavaScript 次數再少 6 倍。
- profiler 的 optimized 模式以前會注入 `requestRenderMode=true`，現在頁面自己做自適應算圖，改成走 app 的合幀＋批次路徑（審查 2026-10-17）。

## 6. 陷阱

- `QTimer.singleShot(ms, 綁定方法)` 對假 self（SimpleNamespace）會 TypeError（PyQt 要 weakref）⇒ 用 lambda。
- 批次鍵名（hdg/spd/vt）不能被 `**_ignored` 吃掉：吃掉就是每架航向 0、機型空，而且完全靜默（測試抓到）。
- JS 範本不能用 `%` 格式化（JS 裡有 `% COLORS.length`、`50%`）⇒ 用佔位字串 replace。
- 2D 頁整頁重繪後 `window._uavMarkers` 歸零，下一批自然重建；注入的 `aeroUavUpdate` 還沒載入時 JS 端 no-op。
- 3D 插值的時間戳不能用「JS 收到的時刻」：30 Hz 合幀會重送同一則 20 Hz 位置、兩批會貼著到 ⇒ 二次外推讓機體倒退（審查實測 90 幀倒退 32 幀）。要用鏈路收到訊息的時刻、只在訊息真的更新時加樣本、顯示時間落後一點做純內插。
- Cesium 的 `allowDataSourcesToSuspendAnimation` 預設 true：任何地物建置都會讓時鐘暫停；飛機取值不要依賴 `clock.currentTime`。
- 跨執行緒的 Qt 信號只傳參考：鏈路要送遙測**快照**，不然 GUI 晚讀時 lat/lon 可能只改了一半。
- `QTimer.singleShot` 預設粗粒度計時器在 Windows 上把 33 ms 拉到 ~48 ms ⇒ 合幀要 PreciseTimer，且串流中連鎖續排。

## 7. 收尾（2026-10-21）：跟著飛機走的疊圖用同一個顯示時間

問題：飛機畫在「現在 − 顯示延遲」（§2 的 3D 列），但 FOV 光錐、SAR 熱力圖掃描、RCS 還用 Python 送來的**最新**遙測 ⇒
18 m/s 時光錐頂點領先模型約 2 m、轉彎時光錐先轉；GPU 填色（Primitive）更只在遙測進來時才動。只改 `main.html`，Python 不動
（`updateFOVCone` 照舊每批送最新值，只用來給視場參數、`alt > 0` 開關，以及沒有該架飛機時的退路）。

| 疊圖 | 改法 |
|---|---|
| 共用 | `_uavShownPose(st)`：模型此刻畫出來的位置與機鼻（`_uavSmoothPos`／`_uavSmoothHpr`）。`_fovDisplayState(sid)`：光錐用的顯示狀態——位置／方向取 `_uavShownPose`，HFOV／VFOV／掛載角／半徑／pitch 取 `updateFOVCone` 傳進來的；同一毫秒共用一次計算；沒有該架 `_UAV_STATE` ⇒ 退回最新值（舊行為）。`_fovApex`：頂點 = 模型位置本身 |
| 光錐邊線／地面框／舊式圓錐 | CallbackProperty 改讀 `_fovDisplayState`（足跡四角也由它算） |
| GPU 填色 | preRender 的 `_fovFillFollow` 每幀對齊。⚠ 順手修掉 **E9**（2026-10-06 無頭實測：填色離飛機 ~76.5 萬 km）：幾何烘在建立當下的世界座標 M0，之後 `primitive.modelMatrix` 放 **M(現在) × M0⁻¹**（以前直接放 M(現在) ⇒ 變換套兩次） |
| SAR 熱力圖 | 消除用**畫面上那個**光錐的足跡；「足跡沒動不累積」的判別量仍是最新遙測那份的 key（顯示狀態每毫秒都在動，用它的話累積速率 = 呼叫頻率） |
| RCS | 威脅用 `_uavShownPose`（顏色染在模型上，對應畫面上的位置） |
| 碰撞警告線 | 本來就讀 `entity.position`（= 顯示時間的內插位置），只加註解與測試鎖 |

方向語意的改變：光錐、RCS 的方向現在是**模型畫出來的機鼻**（定翼／VTOL 非 Q 模式、速度 > 3 m/s 時往航跡混），以前是 Python 另外傳的
VFR_HUD 整數 heading（≈ 機體 yaw）。側風下兩者差一個偏流角（3 m/s 側風、18 m/s 空速約 9.6°）：光錐現在貼著模型轉，但不再顯示偏流。
要看機體真實朝向就把 `_UAV_NOSE_FOLLOWS_TRACK` 關掉（模型與光錐一起改回 yaw）。

驗收（真 Cesium 1.115、無頭 Chrome，`tests/test_cesium_overlay_display_time.py`）：每一幀 postRender 時比較**這一幀 Cesium 實際拿到的值**

填色 = `primitive.modelMatrix × M0`。20 Hz 實時串流、掛載角 20°、60 m 高，三輪各 ~120 幀：

| 指標 | 直飛 18 m/s（航向 30°） | 急轉 30°/s（R 34 m） |
|---|---|---|
| 光錐邊線頂點 vs 模型（最大） | 0.018 m | 0.018 m |
| 填色頂點 vs 模型（最大） | 0.018 m | 0.018 m |

陷阱：
- ⚠⚠ 填色幾何**不能**改成留在機體座標、只靠 `primitive.modelMatrix` 擺：這個 viewer 不是 `scene3DOnly`，Primitive 建立時要把頂點投影成 2D，
  機體座標的點在地心附近 ⇒ `projectTo2D` 丟例外 ⇒ Cesium 把 `useDefaultRenderLoop` 關掉、**整個 3D 靜默停住**（本輪第一版就踩到，
  新測試的 fixture 每條結束都查 `renderError` 與 `useDefaultRenderLoop`）。
- 測試的實時串流第二段要接續軌跡時間：從 t = 0 重來 ⇒ 飛機瞬移回起點、內插拉出假的高速，量到的「領先」會到 9–11 m。
- `tests/test_cesium_uav_batch.py` 的 `resends_add_nothing…` 原本約 1/6 失敗（改動前的 main.html 也一樣，值 0.647998 vs 0.668）：
  `_uavDisplayMs` 與 `JulianDate.now()` 都是毫秒粒度，兩次呼叫跨毫秒 ⇒ frac 差 1/50 = 0.02 正好壓在容差上 ⇒ 改成重取到同一毫秒為止（10/10 過）。
