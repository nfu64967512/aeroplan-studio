# 評估：高精地圖拼接要做成規劃器的分頁（像 Pix4D），還是另開一支程式？— 2026-10-20

使用者：「是否可以在規劃器開一個新的分頁專門處理拼接高精地圖，像 Pix4D 一樣？還是你覺得要另開一個新的專門程式？」
本文件只做評估，**沒有改任何程式**。調查：4 位調查員（程式碼、拼接引擎、架構、作業流程）＋2 位對抗式審查（事實、反方建議）＋綜合；
程式碼的關鍵主張我自己再核對過（第 7 節）。網路資料取得日 2026-10-20。

## 1. 結論

**做在規劃器裡，不另開程式；但不是右側參數面板的一個分頁，也不要自己重做一套 Pix4D。**

- 做成整個視窗的「航測後處理」**工作模式**：切換中央區域，跟規劃器共用同一張 2D／3D 地圖，成果（正射、DSM、照片位姿、檢核點）直接疊在規劃用的地圖上。
- 重的工作不放在規劃器行程裡：
  - **拼接引擎**（ODX／NodeODX）本來就是另外安裝的服務（AGPL 授權、要上百 GB 記憶體），在辦公室那台 128 GB 工作站上跑；
  - **我們自己的前處理**（解日誌、PPK、寫 EXIF、上傳）之後改成子行程，規劃器關掉或當機，工作也不中斷，可以用任務編號接回來。
- 右側參數面板只佔視窗 40%（`ui/main_window.py:1987-1994`），放不下照片網格或 GCP 標點畫面，所以「分頁」要做成整窗模式。
- 自己做一套 Pix4D（照片內標 GCP、點雲／網格檢視、量測、品質報告全自製）估 25–40 人週，不建議；GCP 標點先用 WebODM 內建的 GCP 介面。

**為什麼不另開程式**（現在）：
1. 不論哪個方案，引擎都在行程外，所以「分頁 vs 程式」其實只影響畫面。
2. 支持另開程式的兩個量化理由，複查後都縮小了：上傳時整批照片讀進記憶體是**現有程式的缺陷**（任何方案都要修，改分段上傳即可）；
   在真的 Qt 事件迴圈裡，同行程解析 24 MB 日誌只讓 30 Hz 計時器晚約 5 ms（另一份 64.6% 嚴重延遲的數字來自純 Python 模擬，不適用）。
3. 在這個 repo 另開程式有額外成本：`ui/__init__.py:9` 一匯入就載入整個主視窗（重用任何 `ui.*` 都要 2.3 s、125 MB）；
   實際飛的計畫沒有存進專案檔（HARVEST 區塊只在記憶體裡）；沒有打包設定；唯一現成的獨立程式 `ui/polygon_editor_app.py` 直接執行會匯入失敗。

**什麼時候改成另開程式**：處理改由另一台電腦或另一個人做、要排很多批任務、或地面站要凍結版本做驗證時。到時第 1 步做好的子行程與任務檔就是新程式的核心，不白做。

## 3. 首飛前一定要先修的（不管選哪種容器）

1. **上傳一次把全部照片讀進記憶體**（`survey/odm_client.py:132-135`，單一 multipart POST）：2,300–2,700 張估計尖峰 49–103 GB（照片大小未實測）。改成 NodeODX 的分段上傳。
2. **從沒送 `--force-gps`**：ODM／ODX 一旦拿到 gcp_list，預設就不把照片 GPS 放進平差 ⇒ **我們做的 PPK 公分級位置會被丟掉**。要明確選擇並寫進任務紀錄。
3. 沒記錄引擎與版本；沒讀引擎的品質報告（stats.json、shots.geojson、report.pdf）。
4. 對話框每次開都是新的（`main_window.py:6572`）、關閉時遠端任務會繼續跑卻無法接回；主視窗關閉沒有處理這兩個工作執行緒。
5. 預覽與評估文件裡的記憶體分級要更正：5,300 張要 256 GB 級（評估文件寫「128 GB 或 --split」不夠清楚）。
6. **你**在工作站安裝 ODX＋NodeODX（固定版本），我們先用 200 張做試跑，量照片實際大小、記憶體尖峰、每張秒數、GCP 標點時間。

## 6. 引擎與硬體

- **預設引擎 ODX（經 NodeODX）**：WebODM 於 2026-04-06 與 OpenDroneMap 分家，ODX 是其分支（AGPL-3.0），有 Windows 原生版，最新 v3.8.4（2026-10-18）；
  NodeODX v2.4.0 與我們客戶端用的 REST 端點相同。ODX 會把 gcp_list 裡 `CHK-` 開頭的點當檢核點（上游 ODM 文件沒有這個功能）。
  授權：只以獨立行程／服務呼叫、不隨我們的程式散布；若修改後提供他人網路服務要公開修改的原始碼（非法律意見）。
- **第二引擎（先不買）**：Agisoft Metashape Pro 教育版 USD 549。會在平差中估滾動快門、可輸出 3D Tiles；
  一篇 ISPRS 2025 比較（1,358 張、GSD 1.5 cm）檢核點 RMSE ODM 6.7 cm vs Metashape 3.8 cm，但兩邊設定與量測方式不同、不能直接套到我們的相機。
  首次 ODX 結果不達標或殘差顯示滾動快門問題再考慮。
- **排除**：PIX4Dmatic（訂閱制、沒有官方批次命令列）、DJI Terra（不吃非 DJI 照片）、COLMAP／Meshroom（沒有正射／DSM／GCP 流程）。
- **這台工作站**（實測 128 GB RAM、i7-12700 20 執行緒、RTX 4070 12 GB、D: 2.3 TB 可用、沒裝 Docker／ODM）：
  - **首飛約 2,300–2,700 張：不分塊應可行，有條件**：D: 設 64–96 GB 以上分頁檔、關閉其他程式、預設品質、限制並行約 10–12。時間未知（估 4–12 小時、誤差 2 倍），試跑決定。
    不行就 `--split` 約 1,300–1,400 張一塊（15 個 GCP 夠每塊 3 個以上）。
  - **2×2 km 約 5,300 張：實務上一定要分塊**（3–4 塊、重疊 150 m），估 10–30 小時，有合併失敗的風險。
  - GPU 頂多小幅幫助特徵匹配；記憶體與 CPU 才是瓶頸。現場筆電（規格未知）只做 QA，不做拼接。

## 8. 查核紀錄與未驗證

我自己核對的程式碼：`ui/__init__.py:9`（匯入主視窗）、`survey/odm_client.py:132-135`（單一 POST）、`survey/` 與 `ui/` 沒有任何 force-gps、
`survey_process_dialog.py:1210-1223`（忙碌時關閉只取消本地、遠端任務照跑）、`main_window.py:1987-1994`（面板 40%）、`pipeline.py:1028-1065`（只送正射解析度與滾動快門）。
審查更正的：WebODM 的 GCP 介面**沒有**檢核點功能（是 ODX 本身認 `CHK-`）、該介面不處理高程基準（Z 原樣通過、缺 Z 變 0）、最後一次程式更新 2018 且標實驗性；
`--split` 塊內 GCP 少於 3 個是精度變差不是擋下；「規劃器處理時 64.6% 計時器嚴重延遲」不成立。

**未驗證**：我們的客戶端對真 NodeODX 的任何行為；這台工作站的實際處理時間與記憶體；樹莓派 HQ 照片實際檔案大小；滾動快門讀出時間（84–87 ms 是推估）；
WebODM 的 GCP 介面與 ODX 版 WebODM 相容；現場筆電規格；PPK 是否放寬每塊 3 個 GCP 的規則；所有人週與評分都是判斷不是量測。
